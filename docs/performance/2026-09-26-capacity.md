# Note and notebook capacity, 26 September 2026

The requested 100-page and 1,000-page notes passed the automated editor checks. A folder containing 1,000 notes also passed the rendering and search checks. These are promising baseline results, not a supported maximum or a complete native-app usability test.

A page means **500 words**. The two manual notes contain exactly 50,000 and 500,000 words, excluding Markdown syntax and frontmatter. Each page has one heading and five paragraphs. The small notes contain roughly 500 words, a unique search marker, task items, and inline formatting.

The test machine has an Apple M5 Pro, 48 GiB RAM, and macOS arm64. Browser tests use headless Playwright WebKit with the actual `NotesEditor`, `NotesPane`, Markdown conversion, document parsing, and search modules through Vite's development server. Native tests use release-mode Rust functions on disposable local folders. Timing values are observations on this machine, not CI pass/fail thresholds.

## What is the limit?

No configured word-count or note-count ceiling was found in the inspected editor, storage, and search paths. No correctness failure occurred through 5,000 pages or 10,000 notes in these workloads. This does not establish a hard maximum. Available memory, document structure, browser layout, attachment sizes, and filesystem behavior all affect it.

For prose notes, 100 and 1,000 pages look viable for manual testing. At 2,000 pages, the opening delay exceeds two seconds. At 5,000 pages, opening takes about 14.5 seconds and a ten-transaction burst occupies the main thread for about 0.2 seconds. I would not call that a comfortable working size. The practical threshold for this prose workload lies between the 1,000-page and 5,000-page cases, depending on how much delay is acceptable.

For notebooks, 1,000 small notes look viable. At 5,000 notes, search and list interactions introduce noticeable delays. At 10,000 notes, some queries block for over a second. Splitting notes across folders reduces the number of rendered cards, but does not reduce the cost of global search. The current implementation renders every card in the selected folder and constructs a Fuse index on each query. Notebook opening also reads all contents and rebuilds the link index. These are the first areas to investigate if larger notebooks become a product requirement.

There is no reason to introduce an arbitrary limit at 1,000 pages or 1,000 notes based on these measurements. There is also not enough evidence to promise unlimited capacity.

## Correctness coverage and limits

The browser runner checks that every page loads, edits at the beginning/middle/end are captured, all page headings survive saving, no parent update occurs during a synchronous typing burst, one deferred parent update contains the final edit, serialized echoes preserve the ProseMirror document object, and undo removes the final marker. It checks that all note cards render, the last card becomes selected, and search finds note 1,000. Each size starts in a fresh browser process. Each search query runs three times.

The native test checks note and content counts, index population, complete long-note contents, and exact readback after saves. Its small notes contain one link to the next note. Native long-note fixtures use longer repeated words, so their byte sizes are larger than the browser fixtures at the same word count. JSON encoding is measured separately from snapshot construction.

These tests do not measure the complete Tauri UI, IPC delivery/decoding, cold Google Drive downloads, sync conflicts, watcher storms during generation, long-session memory growth, image-heavy notes, large tables, syntax highlighting, outline rendering, export, real keyboard-to-paint latency, or sustained scrolling. Browser opening includes two animation frames; burst measurements time synchronous ProseMirror transactions. Capture includes DOM reconciliation and Markdown serialization, not disk writes. Native timings are on newly generated local files that can already be in the OS cache. There is no crash-limit or memory-exhaustion claim.

## Reproduce

Create a fresh set in an existing notebook. The generator refuses to reuse an existing destination folder and does not overwrite notes:

```sh
node scripts/create-stress-notebook.mjs '/path/to/notebook' 'New capacity test'
```

Start the development server, then run the browser checks in a second terminal. Supply an installed Playwright module path if Playwright is not on the project's module search path. Its matching WebKit browser must be installed. `PLAYWRIGHT_BROWSERS_PATH` can select an existing browser cache.

```sh
npm run dev -- --port 1433
node scripts/check-stress.mjs /path/to/playwright http://localhost:1433 /tmp/tigrana-stress-results.json
```

The runner tests 100, 1,000, 2,000, and 5,000 pages; 1,000, 5,000, and 10,000 notes; and search across 1,000 notes plus the two large documents. Cases have a 90-second timeout and stop increasing that workload after a failure. Results are checkpointed after each case. The browser fixture is development-only and is not part of the production app entry point.

```sh
cargo test --manifest-path src-tauri/Cargo.toml --release stress_notebook_capacity -- --ignored --nocapture
npm test -- src/editor/NotesEditor.performance.test.tsx src/App.performance.test.tsx src/lib/search.test.ts
npm run lint
npm run build
npm run tauri -- build --bundles app
```

The native stress test is ignored during ordinary test runs to keep them fast. It creates and removes its own temporary notebooks. It never accesses the user's notebook.
